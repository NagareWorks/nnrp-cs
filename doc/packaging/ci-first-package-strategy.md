# CI-First Package Strategy

The repository does not stage Unity package trees, generated DLL folders, or native binary payloads as source. Package outputs are generated by CI from checked-in project files, package metadata, scripts, and the pinned `nnrp-rs` native artifact release.

This policy exists so reviewers can distinguish source changes from generated release content. If a pull request changes package output, it should change the owning project metadata, release workflow, package-generation script, or tracked OpenUPM metadata instead of committing generated package payloads.

## Sources Of Truth

- Version metadata comes from the shared MSBuild properties used by the SDK projects.
- NuGet package contents come from the SDK project files and `dotnet pack`.
- Native bridge payloads come from the pinned `nnrp-rs` release and are resolved by `scripts/download_nnrp_rs_artifacts.py`.
- Unity package metadata starts from `Packages/com.nnrp.client/package.json` and `Packages/com.nnrp.client/README.md`.
- Unity package layout, managed assembly copy, native plugin copy, and deterministic `.meta` files are generated by `scripts/build_upm_package.py`.
- Release gating and publication rules live in `.github/workflows/release.yml`.

## Release Outputs

The release workflow resolves native artifacts first, then builds and tests the managed SDK before packaging.

Expected outputs are:

- NuGet packages produced under `artifacts/packages`.
- A bundled NuGet artifact named `nnrp-cs-nuget-<version>.zip`.
- A generated Unity package tree under `artifacts/upm/com.nnrp.client`.
- Unity fallback release bundles named `com.nnrp.client-<version>.zip` and `com.nnrp.client-<version>.tgz`.

Unity projects should install `com.nnrp.client` from OpenUPM when possible. GitHub Release Unity bundles are fallback artifacts, not the repository source of the Unity package tree.

## Reviewer Policy

Reject package changes that:

- Add generated `bin`, `obj`, Unity-generated `.csproj`, or staged DLL folders.
- Commit native `.dll`, `.so`, `.dylib`, or `.a` payloads outside the generated release artifact flow.
- Hand-maintain Unity plugin `.meta` files for generated package payloads instead of updating `scripts/build_upm_package.py`.
- Move platform plugin paths without updating the package-generation tests and release documentation.
- Treat Unity package contents as a checked-in source tree rather than a CI product.

Accept package changes when the source of truth is updated and the generated output can be reproduced from CI. Typical acceptable changes include project package metadata, release workflow behavior, native artifact mappings, deterministic Unity importer settings, or tracked OpenUPM package metadata.

## Local Validation

Use the narrowest commands that prove the touched packaging slice:

```powershell
python scripts/build_upm_package.py --repo-root . --tracked-output Packages/com.nnrp.client --validate-tracked-metadata --repository-url https://github.com/NagareWorks/nnrp-cs
python -m unittest discover -s tests/Packaging.Tests -p "test_*.py"
dotnet build Nnrp.sln --configuration Release
dotnet test Nnrp.sln --configuration Release --no-build
dotnet pack Nnrp.sln --configuration Release --no-build --output artifacts/packages
```

When validating the generated Unity package locally, provide a native artifact root that matches the RID layout produced by `scripts/download_nnrp_rs_artifacts.py`, then run:

```powershell
python scripts/build_upm_package.py --repo-root . --configuration Release --native-root artifacts/native --output artifacts/upm/com.nnrp.client --repository-url https://github.com/NagareWorks/nnrp-cs
```

Do not commit the generated `artifacts` tree after local validation.
